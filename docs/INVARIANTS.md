# Core System Invariants

The following 28 invariants are non-negotiable architectural and operational laws governing the **CoinDCX Quant Futures Bot**. No feature, performance optimization, refactoring, or hotfix may violate these rules.

---

### Invariant 1: CoinDCX Only
The platform integrates exclusively with CoinDCX. No generic multi-exchange abstraction layers, adapters, or cross-exchange routing logic shall be introduced into the codebase.

### Invariant 2: INR Futures Only
Trading logic, margin calculations, collateral tracking, and PnL reporting operate exclusively on CoinDCX INR-Margined Perpetual Crypto Futures contracts. Spot, Options, and foreign currency contracts are strictly barred.

### Invariant 3: Single User
The bot is engineered for a single user operating a single CoinDCX account. Multi-tenancy, authentication delegation, and user role isolation layers are out of scope and prohibited.

### Invariant 4: No Coin-Specific Hardcoding
Coin-specific values (e.g., symbol names, tick sizes, step sizes, price precision, min/max notional limits, leverage brackets) must never be hard-coded into core trading, risk, or data engines. All instrument parameters must be supplied via dynamic exchange metadata discovery or external coin configuration.

### Invariant 5: Modular Coin Onboarding
Onboarding a new coin (such as SOL) must never require altering the core engine, risk calculators, order state machines, or database schemas. All coin additions are strictly driven by configuration and verified historical data backfill.

### Invariant 6: Canonical 1m Market Data Truth
The finalized 1-minute candle is the foundational source of truth for all quantitative analysis. All market data ingestion paths converge onto canonical 1m candles stored in MySQL.

### Invariant 7: Higher Timeframe Derivation
All configured higher timeframes (including the initial production-supported set: 2m, 3m, 4m, 5m, 10m, 15m, 30m, 1h, 4h, 1d) must be mathematically synthesized exclusively from authoritative canonical 1m candles using exact constituent completeness without data fabrication. The core aggregation engine is strictly generic for safe integer durations (`timeframeMinutes: integer >= 2`, preserving canonical 1m exclusivity in Phase 5) and must not hardcode timeframe durations or coin symbols. All operations must be serialized per pair and strictly gated by upstream canonical health; derived aggregate sums must maintain exact decimal precision without silent truncation. Exchange-provided higher-timeframe candles must not be used as authoritative data sources.

### Invariant 8: Stale Data Protection
Incomplete, missing, or stale market data must immediately inhibit new live trade entries. If the latency between the current timestamp and the latest finalized candle exceeds predefined safety thresholds, signal processing for that instrument must halt.

### Invariant 9: Complete Strategy Decoupling
Strategies are pure analytical components. A strategy cannot access network sockets, call exchange APIs directly, query account balances, or construct execution orders. Strategies emit only abstract signals (`LONG`, `SHORT`, `FLAT`) with confidence and intent parameters.

### Invariant 10: Non-Bypassable Risk Engine
All strategy signals must pass through the central Risk & Leverage Engine before reaching the execution layer. There is no execution path in the software that bypasses risk validation.

### Invariant 11: Invariant Core Safety Controls in High Risk Mode
Selecting `HIGH` risk mode may elevate leverage caps or position sizing parameters, but it must never disable core safety controls, invariant circuit breakers, liquidation buffers, or exchange kill switches.

### Invariant 12: Idempotent Order State Management
An order with an unknown, pending, or ambiguous state must never be blindly retried or re-submitted. The system must query exchange ground-truth or wait for reconciliation before taking remedial action.

### Invariant 13: Fill-Derived Position Truth
A position's size, average entry price, and realized PnL are determined solely by confirmed exchange execution fills, never by sent order quantities or unconfirmed optimistic state updates.

### Invariant 14: Mandatory Startup Reconciliation
Reconciliation between local database records and actual CoinDCX open positions, orders, and balances must complete successfully before any live strategy execution loops are initialized.

### Invariant 15: Crash Recovery Idempotency
Application restart, process crashes, or infrastructure reboots must never cause duplicate orders or duplicate positions. Startup routines must discover existing active orders and reconcile them with active state machines.

### Invariant 16: Zero Credential Leakage
API credentials, API secrets, signing keys, and session tokens must never be written to application logs, exposed in HTTP error responses, emitted over telemetry, or committed to version control.

### Invariant 17: Uniform Strategy Implementation
The identical strategy code and logic that executes in live trading must be used in backtesting, paper trading, and shadow mode. No separate "live" and "simulation" strategy forks are permitted.

### Invariant 18: Realistic Cost Modeling
Backtesting and simulation environments may claim complete exchange economics only when they account for realistic taker/maker trading fees, provider-authoritative per-instrument perpetual funding, and market impact slippage. A universal 8-hour funding interval is prohibited. Any environment lacking authoritative funding must disclose that exclusion and is ineligible to provide production-promotion evidence.

### Invariant 19: Full Audit Lineage
Every production trade must be completely traceable from end to end:
`Signal Generation` → `Risk Evaluation` → `Execution Intent` → `Exchange Order` → `Execution Fills` → `Position Update` → `Position Exit`.

### Invariant 20: Explicit Live Trading Activation
Live trading capabilities must remain physically disabled until explicit, multi-phase verification is complete and later-phase activation approval is granted. Live order placement code paths must not exist in early foundations.

### Invariant 21: Deterministic Historical Datasets & Zero Data Fabrication
Historical 1-minute research datasets must be acquired exclusively from genuine CoinDCX Futures closed candlestick REST data, persisted directly to the single canonical `candles_1m` store under the exact same `CanonicalDecimal` and structural OHLC validation as live candles, and identified deterministically by SHA-256 content hashing of logical market truth. Missing intervals must be retrieved genuine from the exchange or marked incomplete; synthetic gap fabrication (interpolation, forward-filling, previous-close copying, zero-volume insertion, or silent minute skipping) is strictly prohibited. Historical backfill and import write operations must execute as offline tasks without concurrent live Phase 5 writers.

### Invariant 22: Deterministic Indicator Engine & Zero Lookahead
Technical indicators derive strictly from closed, validated Phase 5 canonical 1m (`CanonicalCandle1m`) or Phase 6 higher-timeframe (`HigherTimeframeCandle`) candles through pure, deterministic decimal arithmetic. All calculations execute within an unbroken calculation segment bound to an explicit `bootstrapStartOpenTimeMs`. For recursive indicators, exact state and output parity across restarts requires replaying continuous closed candles from the identical bootstrap origin (claims that "recent warmup candles" can reconstruct an existing recursive state are strictly barred). All intermediate calculations execute within an isolated 128-digit decimal context (`IndicatorCalcDecimal`, `ROUND_HALF_UP`) with native floating-point math strictly forbidden, producing immutable `IndicatorDecimal` outputs quantized to maximum 18 decimal places without feeding rounded values back into recursive state machines. The engine enforces prefix determinism (zero lookahead within the calculation segment; output at candle $t$ depends only on candles $\le t$), strict stream continuity (failing closed on gaps, duplicates, or out-of-order candles without synthetic interpolation or forward-filling), exact batch/incremental parity (batch execution feeds the identical incremental state kernel), complete state isolation (no module-global mutable state; independent instances across pairs, timeframes, parameters, and bootstrap origins), deterministic warmup semantics (emitting `null` before mathematical readiness, never `0`, `NaN`, `Infinity`, or fake seeds), universal period parameter bounds ($1 \le period \le 100\,000$), bounded memory guarantees ($O(period)$ for rolling indicators, $O(1)$ for recursive states, never accumulating total run history), runtime midnight safety for UTC-day VWAP (rejecting candles spanning two UTC calendar days), and zero indicator database persistence (state is reproducible via segment replay). Authoritative Volume Profile calculation is strictly deferred pending canonical trade-level price-volume data; synthetic intrabar volume distribution heuristics are barred. Identical closed candle truth with identical parameters and identical bootstrap origin must yield bit-for-bit identical indicator outputs.

### Invariant 23: Deterministic Backtesting & Causal Execution
Every research backtest must bind cryptographically to a verified Phase 7 canonical 1m dataset under a two-pass contract: Pass 1 verifies the complete manifest range `[fromInclusiveMs, toExclusiveMs)` against Phase 7 canonical logical-row hashing primitives (`encodeHistoricalLogicalRow`, `canonicalHashDecimal`, `computeDatasetId`), and Pass 2 streams the replay span `[bootstrapFromInclusiveMs, replayToExclusiveMs)` from the identical immutable source; accepting a valid manifest paired with a substituted candle stream is strictly prohibited. The backtest executes in one strictly ordered causal timeline across safe integer, 60-second aligned boundaries with common bootstrap alignment across all configured higher timeframes and Phase 8 indicator kernels bound to actual derived candle origins. A decision or cancellation accepted at timestamp $T$ may depend only on market data closed by $T$ and becomes effective at the next source bar open at $T$ before any fills, with cancellations winning over opening gap-throughs. Simulated execution must enforce conservative 1m OHLCV rules: all-or-none fills with zero queue or partial-fill fabrication; strictly positive execution prices ($> 0$); raw `bar.OPEN` post-only marketability rejection; resting limit strict penetration (`bar.low < limitPrice` for BUY, `bar.high > limitPrice` for SELL; touches never fill); gap-through stop pricing; intrabar OCO ambiguity resolved via `ADVERSE_FIRST` candidate selection merged into a global `orderSequence` ascending total order; and whole-order rejection for reduce-only excess without partial reduction or reversal. All financial math executes in an isolated 128-digit Decimal context (`BacktestCalcDecimal`, `ROUND_HALF_UP`) under a single-currency deterministic accounting ledger: reversal realized PnL is computed strictly on closing quantity with single fee assessment; net PnL and equity identities are exact; non-negative spread/slippage attributions are tracked without double-deduction; and causal funding schedules operate strictly within `(bootstrapFromInclusiveMs, replayToExclusiveMs]` emitting exactly one `FUNDING_APPLIED` per scheduled event applied to surviving positions before evaluation. At replay completion, terminal open positions and unresolved orders (`terminalOpenOrders`) are disclosed without synthetic liquidation, fake fees, or fake cancellations. Run inputs are defensively normalized and deeply frozen before `runId` computation; `maxOpenOrders` is bound in manifest identity; core replay memory is bounded to $O(\text{working state})$; and event sink failures fail closed immediately (`isValid = false`, terminal `FAILED`). Pure Phase 10 strategy logic remains completely decoupled from simulator mechanics. Identical dataset + configuration + participant behavior + code identity must produce bit-for-bit identical ordered events, fills, accounting, `runId`, `eventLedgerSha256`, and `resultSha256`.

### Invariant 24: Environment-Neutral Deterministic Strategy Decisions
The exact same pure strategy code, kernel classes, and decision logic that execute in live trading must be used in backtesting, paper trading, and shadow mode without environment-specific forks, conditional execution branches, or simulation superpowers. Pure strategy kernels in `src/strategies/core/**` consume only immutable, sanitized closed-market truth and finalized Phase 8 indicator values; they never consume account equity, cash balances, exchange positions, active open orders, margin state, execution fills, network clients, or wall-clock timestamps (`Date.now()`, `new Date()`). Before evaluating warmup or signal logic, all required indicator bindings must be structurally validated for presence, pair match, timeframe match, closed timestamp validity, trigger freshness, and higher-timeframe freshness; missing or mismatched indicators fail closed and never silently become warmup or flat. Once an indicator has produced a valid non-null point in a continuous segment, regressing to null fails closed as an unrecoverable input violation. All calculations execute in an isolated 128-digit decimal context (`StrategyCalcDecimal`, `ROUND_HALF_UP`) with native floating-point math strictly prohibited. Strategies do not execute orders, calculate position sizing, or choose leverage; they emit only abstract target exposures (`LONG`, `SHORT`, `FLAT`) bound to a deterministic `decisionSequence` and cryptographic `decisionId` calculated over canonical decision content bytes. Legitimate indicator warmup emits non-actionable `status: 'WARMING'` with `targetExposure = null`; converting warmup into `FLAT` or generating exit orders during warmup is strictly prohibited. Every actual trigger evaluation must successfully write an immutable `StrategyDecision` to a durable `StrategyDecisionSink` before any environment adapter reconciliation occurs; if the audit sink fails, the adapter must fail closed with zero order output. Indicator mathematics must not be reimplemented within strategy code; all analytical inputs derive from genuine Phase 8 `IndicatorKernel` instances bound to explicit per-timeframe calculation segment bootstrap origins (`indicatorBootstrapIdentity`) that authoritatively bind `strategyInstanceId`. Decimal strategy parameters are lexically canonicalized so that numeric equivalents (`"2"`, `"2.0"`, `"002.000"`) produce the identical `parameterHash`. Adapter-only behaviors, including `fixedResearchQuantity`, remain outside pure strategy parameter hash and must deterministically bind environment participant and run identity (`runId`). Identical closed market truth + identical Phase 8 indicator truth + identical strategy version, parameters, and per-timeframe bootstrap origins must produce bit-for-bit identical decision sequences, decision IDs, statuses, target exposures, and machine-readable reason codes across all environments.

### Invariant 26: Deterministic Research Validation & Statistical Robustness
Statistical validation of quantitative research candidates explored in Phase 11 must execute as a strictly deterministic, chronological, and fail-closed validation engine. Validation policies, candidate spaces, walk-forward windows, holdout boundaries, cost stress scenarios, Monte Carlo parameters, and approval thresholds are defensively deep-copied and deep-frozen into an immutable `ResearchValidationPlan` identified cryptographically by `validationPlanId = sha256CanonicalJson(plan)`; post-construction caller mutations have zero effect on frozen identities or execution. All temporal validation must strictly progress chronologically; random train/test row splitting, K-fold row shuffling, and backward-looking evaluations are strictly prohibited (zero lookahead). Walk-forward analysis (`P12_WALK_FORWARD_V1`) configures day-aligned, non-overlapping out-of-sample (OOS) evaluation windows with $\text{stepDays} === \text{testDays}$, deriving total folds $K = \max\{j \ge 1 \mid \text{OOS\_end}(j-1) \le \text{holdoutStartMs}\}$ and canonically reporting any unused tail calendar duration ($\text{unusedTailMs} < \text{stepDays} \times 86\,400\,000$); indicator bootstrap warmup is strictly quarantined before the active evaluation window, and zero warmup data may enter validation metrics or return series. An explicit final holdout window is placed chronologically strictly after all walk-forward development folds, frozen inside `validationPlanId`; holdout integrity is governed by explicit operator attestation (`holdoutExposureDeclaration: 'UNSEEN_BY_OPERATOR' | 'PREVIOUSLY_OBSERVED'`), barring false cryptographic claims of historical data freshness. Phase 12 must capture evidence strictly from the authoritative Phase 11 `executeCell` $\to$ Phase 9 `BacktestEngine` execution path via an execution-only `eventSinkFactory` observer seam; constructing secondary backtest simulators or reconstructing PnL from raw OHLCV candles independently is strictly prohibited. The streaming evidence collector captures the minute-close mark-to-market equity path (`ACCOUNT_MARKED` events post-funding flush), funding debits/credits, closed trade gross PnLs, and fills. Generic parameter neighborhood sensitivity measures plateau stability without hardcoding strategy-specific parameters in core validation code. ### Invariant 27: Non-Bypassable Deterministic Risk / Leverage Authority Hierarchy
Every genuine Phase 10 `StrategyDecision` with `status === 'READY'` accepted for sizing must pass through a single, pure, deterministic Risk / Leverage Engine that evaluates an immutable `RiskEvaluationContext` and emits an auditable `RiskDecision`; a `status === 'WARMING'` decision is a structural non-actionable no-op and never reaches the engine. There is no code path that constructs a sized quantity or an approved leverage value outside this engine, and the engine binds only the real Phase 10 contract (`decisionId`, `decisionSequence`, `strategyInstanceId`, `strategyId`, `strategyVersion`, `parameterHash`, `pair`, `evaluationTimeMs`, `triggerTimeframeMinutes`, `status`, `targetExposure`, `reasonCodes`) — it never assumes `StrategyDecision` carries price, leverage, or quantity, and independently recomputes `decisionId` via the genuine kernel hash formula before trusting it; entry price, stop price, and any leverage recommendation are separate, versioned, provenance-bound proposals from a distinct upstream source, never fields fabricated onto the strategy decision itself. `side`/`action` (`OPEN`, `CLOSE`, `NO_CHANGE`, or `REVERSAL_DEFERRED`) are derived deterministically from `targetExposure` plus the authoritative current position (Invariant 13); there is no partial-reduce action and no atomic reversal in V1, because no upstream input contract supplies a target quantity — `CLOSE` always means full closure of the requesting strategy instance's proven owned share of the existing position — ownership is authoritatively keyed by the complete `strategyInstanceId` + `strategyId` + `strategyVersion` + `parameterHash` tuple, never by `strategyInstanceId` alone and never by `strategyId` alone (two instances of the identical strategy definition on the same pair must never be able to close or reduce each other's share, and a `strategyInstanceId` match paired with any mismatched configuration field is rejected as an identity inconsistency, never trusted), ownership state is represented as a discriminated flat-versus-open union in which a flat pair carries no position identity at all (never a fabricated placeholder) while an open position requires a genuine exchange position identity, an exchange-aggregated position lacking a proven per-instance ownership breakdown — including one whose reported quantities or reported current INR notionals fail to reconcile to the authoritative aggregate — fails closed for `CLOSE` rather than assuming sole ownership, current-instance notional is never adapter-discretionary but is derived by one frozen, policy-versioned valuation method (authoritative mark price times contract multiplier times the authoritative settlement conversion rate, quantized exactly once into a single shared per-unit valuation factor that every instance and the aggregate are then multiplied against) so that no instance may be valued on a different basis than the aggregate, is recomputed by the engine rather than trusted as reported so a supplied aggregate notional can never bypass reconciliation, is compared under exact canonical decimal equality with no tolerance band of any kind, and fails closed as unreconciled whenever the authoritative mark price is unavailable rather than substituting the position's historical average entry price or its historical average conversion price; CoinDCX's signed authoritative position quantity is converted to an unsigned magnitude plus a separate direction label at exactly one normalization boundary, after which no signed quantity exists anywhere in ownership reconciliation — every per-instance owned quantity is a strictly positive canonical magnitude (a zero share is represented by omitting the record entirely, never by a zero-valued entry that could serve as a fake allocation), per-instance direction is inherited from the authoritative open position and is never encoded in the sign of a quantity, and an instance can therefore never represent the opposite direction inside the same one-way position, so a mixed-sign instance set can never cancel into a falsely reconciling aggregate; and — because unattributed existing exposure may already belong to another instance — an unreconciled ownership state fails closed identically for `OPEN`, never exempted merely because the new exposure is nominally separate; a reversal is deferred to two independently-evaluated sequential decisions. Authority over every decision-affecting field (risk-per-trade/budget, max leverage, max quantity, max notional per trade, global/pair/strategy exposure, max concurrent positions, daily loss, drawdown) is governed by an explicit field-by-field authority matrix in which every layer — global config, pair config, strategy proposal, selected risk mode, optional per-trade override, CoinDCX dynamic leverage-tier evidence, and account/exposure gating state — is classified exactly `PROPOSE`, `TIGHTEN`, `HARD_CAP`, or `NOT_APPLICABLE` for that field; `NOT_APPLICABLE` is never coerced to an unlimited/`Infinity` value, every `TIGHTEN` relationship is validated once at configuration load time (never per-trade), and a widening `RiskModeConfig`, `PairRiskConfig`, or `RiskOverride` fails closed as a configuration error before any decision is constructed. Selecting `HIGH` or `CUSTOM` risk mode may raise `riskPerTradePercent`, `maxNotionalPerTradeInr`, or `leverageRecommendation`, but these values participate in the same authority matrix as every other mode and can never bypass CoinDCX's dynamic exchange leverage tiers, account/exposure hard caps, or the global/pair configuration ceiling (Invariant 11 structurally enforced, not merely documented). Position sizing first computes a fixed risk-budget quantity ceiling from a risk budget and stop distance using isolated 128-digit Decimal arithmetic (`RiskCalcDecimal`, `ROUND_HALF_UP`) with every quantity-limiting rounding truncated toward zero to the discovered `quantityIncrement`, guaranteeing realized risk never exceeds the nominal risk budget; native floating-point math, `parseFloat`, and `Math.random` are strictly forbidden in all risk arithmetic. Leverage and final quantity are resolved together by exhaustively enumerating every CoinDCX leverage tier exactly once in a single finite pass bounded by tier count — for each tier deriving its implied leverage cap, its margin-limited quantity, and the intersection with the risk-budget ceiling, the instrument's `maxQuantity`, the instrument's own `maxNotional`, the resolved max-notional-per-trade cap, remaining exposure headroom, and that tier's own adapter-verified notional interval (explicit inclusive/exclusive bounds, never derived by the engine from a bare leverage/cap pair) — and selecting the greatest feasible quantized quantity across all tiers; this is not an iterative shrinking fixed-point search and does not depend on evaluation order, and it fails closed with `NO_VALID_LEVERAGE_TIER` (or the more specific margin/minimum-size code) when no tier yields a feasible candidate. CoinDCX leverage-tier and margin data must be consumed exclusively from a normalized adapter snapshot bound to the genuine Phase 2 read-layer `dynamicPositionLeverageTiers`/`dynamicSafetyMarginTiers` models, carrying an explicit tier-boundary semantics disclosure (`VERIFIED` vs `SEMANTICS_UNVERIFIED`) since CoinDCX's inclusive/exclusive tier-boundary behavior is not authoritatively documented, and new exposure fails closed while unverified; hardcoding exchange leverage limits as production truth or fabricating tier data when unavailable is strictly prohibited. Freshness for every evidentiary snapshot (account, pair, exposure, leverage-tier, settlement-rate) is governed exclusively by a risk-policy-owned maximum-age configuration, itself canonically hashed into a freshness-policy identity that is bound into the overall risk-policy identity so that changing any decision-affecting max-age necessarily changes every downstream decision identity rather than silently altering outcomes under an unchanged one, compared against `RiskEvaluationContext.evaluationTimeMs` — snapshot evidence may never declare its own trust window, the pure engine reads no wall clock, causal ordering (source time at or before observed time, observed time at or before evaluation time) admits zero tolerance inside the engine — any operational clock-skew allowance is strictly an adapter responsibility applied before a snapshot is ever constructed — and every snapshot's declared source identity is independently checked against a policy-owned expected source authority that no evidence can itself assert or widen. `estimatedInitialMarginUsdt`/`estimatedInitialMarginInr` (notional divided by final leverage) are initial-margin estimates only; Phase 13 does not compute progressive maintenance margin or a liquidation price absent authoritative confirmation of CoinDCX's exact tranche semantics, and never represents notional-over-leverage as complete liquidation or maintenance-margin truth. Exposure limits (global, pair, strategy, concurrent positions) are evaluated as gross absolute notional sums, never netted against opposite-direction positions on different pairs, and pending/reserved exposure is a discriminated `KNOWN`/`UNKNOWN` state that fails closed for any exposure-increasing action when `UNKNOWN` — it is never defaulted to zero. Daily loss and drawdown circuit breakers evaluate a realized-only net daily PnL (realized trading PnL plus funding minus fees plus other adjustments, explicitly excluding unrealized mark-to-market) over `[UTC day start, evaluationTimeMs]` against an equity figure that does include unrealized PnL, clamped to a non-negative loss magnitude (`max(0, -netDailyPnlInr)` — a profitable or breakeven day always contributes zero loss magnitude, and the signed net figure is never compared directly against a positive limit), gated primarily by direct comparison against a required, strictly positive, resolved INR cap (`>=` rejects at the boundary) with any percentage-of-equity variant treated strictly as a separate, optional, independently-reasoned secondary gate rather than a substitute for the direct comparison; all thresholds are configuration-driven with zero adaptive or ML-derived adjustment, and none of `currentEquityInr`, `peakEquityInr`, daily PnL components, consecutive-loss count, or cooldown state may be attributed to the existing CoinDCX wallet read-layer model, which does not compute derived account equity — these are the responsibility of a distinct, not-yet-implemented account-risk-state adapter whose output contract Phase 13 defines but does not build. The engine differentiates exactly two failure universes: static configuration-object malformation (a widening override, a hierarchy violation, a non-finite config decimal, an unsupported risk mode) throws before any decision of any kind is constructed, while malformed per-evaluation evidence (missing/unknown fields, invalid types, unparseable or non-finite Decimals, or prohibited non-canonical Decimal forms under the risk spec §11.1) throws `RISK_SOURCE_INVALID` only when canonical evidence identity cannot be established. Once canonical identity is established for the incoming evidence, `RISK_SOURCE_INVALID` is unreachable and every per-evaluation failure terminates as a fully auditable, discriminated `RiskDecision` (`AcceptedOpenRiskDecision | AcceptedCloseRiskDecision | RejectedRiskDecision`) — a declared decision/evidence identity hash differing from canonical recomputation is always this latter, deterministic rejection outcome, never a thrown failure, provided the underlying object was well-formed enough to compute an identity from at all — and this boundary admits no exception for valuation evidence, whose bound multiplier, conversion rate, or valuation-method version disagreeing with the surrounding evidence is likewise a deterministic rejection participating in normal reason precedence rather than a thrown construction fault, as is a valuation whose inputs are each individually valid but whose required arithmetic cannot be completed within the frozen decimal context, and identity-mismatch reasons are correspondingly narrow — reserved for identity and hash recomputation alone, never for numeric value reconciliation, which belongs to the reason code owning that reconciliation (`POSITION_OWNERSHIP_UNRECONCILED` for valuation amounts). Source authority is a separate check: expected versus actual `sourceId` disagreement yields `SOURCE_ID_MISMATCH`, declared `contentSha256` disagreement with canonical recomputation yields `DECISION_IDENTITY_MISMATCH`, and valuation context exhaustion yields `VALUATION_NUMERIC_CONTEXT_EXCEEDED`; every breach of the universal causal ordering, settlement conversion evidence included, is reported as a temporal-causality violation, while each per-snapshot staleness code is reserved exclusively for causally valid evidence that merely exceeds its policy age limit, so a future-dated rate is never understated as ordinary staleness; whenever more than one rejection condition is simultaneously true, the resulting primary and secondary reason codes are ordered exclusively by one frozen, self-validating global precedence table covering every rejection code exactly once, never by incidental object, array, map, or set iteration order — a rejection can never carry populated approved financial values (`approved: null`, enforced structurally by the union, not by convention), and every applied cap is disclosed as an explicit resolved value, a genuine not-applicable, or an unresolved placeholder, never a fabricated zero. `riskDecisionId` and `positionSizingDecisionId` are computed via the repository's single canonical-JSON SHA-256 hasher over the frozen policy identities and independently-computed content hashes of every snapshot, with every decimal value canonically normalized so that numerically equivalent strings hash identically and every canonical input validated against an exact expected field shape so no unknown field can silently enter or escape the hash, strictly excluding wall-clock reads, host/PID/worker identifiers, and mutable object ordering; identical canonical input must produce a bit-for-bit identical `RiskDecision`. An `ACCEPTED` decision is valid only for the exact evidence snapshots and evaluation time bound into its identity and is never a guarantee of future safety; later execution and reconciliation phases must revalidate all decision-affecting state before any external mutation, while the engine itself performs zero I/O, zero persistence, and zero order construction — it produces read-only, replayable risk evidence only, and never constructs an `ExecutionIntent`, executes a paper or live order, or ranks/promotes a strategy (Phase 14 owns paper execution, Phase 15 owns ranking, Phase 17 owns live execution).

### Invariant 28: Phase14 Paper Funding Is Explicitly Unsupported
CoinDCX paper execution currently operates with the single immutable capability `FUNDING_UNSUPPORTED` because first-party provider evidence is insufficient to reproduce settlement-authoritative perpetual-funding economics. No `FUNDING` ledger entry may be created, and account/position `cumulativeFundingInr = 0` means only that no authorized paper funding posting was made; it does not prove economic funding was zero, no boundary occurred, no funding was due, or the position was ineligible. All paper PnL/equity is labeled `FUNDING_EXCLUDED` and validates mechanics rather than CoinDCX economic parity. Funding-excluded evidence cannot authorize `PAPER_APPROVED`, `SHADOW`, `LIVE_CANDIDATE`, or `LIVE`; there is no intraday or short-hold exemption. Missing funding must never be replaced by zero, a current rate, or fabricated history, and private real-position settlements must never be mapped to synthetic paper positions.

Economic funding may be enabled only after the CoinDCX provider gate is reopened and first-party, production-supported evidence proves the settlement-authoritative rate; estimate-to-final transition; settlement and schedule-change timing; exact boundary eligibility; mark/notional basis; INR conversion and rounding; historical applied-rate recovery; deterministic event identity; and duplicate, correction, replay, and late-arrival behavior. No third-party exchange or aggregator may substitute for CoinDCX authority.
