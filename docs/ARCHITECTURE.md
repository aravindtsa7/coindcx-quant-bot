# System Architecture

## 1. Architectural Philosophy

The **CoinDCX Quant Futures Bot** is built as a highly deterministic, modular TypeScript monolith backed by MySQL 8. It adheres strictly to:
- **Separation of Concerns:** Each module encapsulates a single domain with explicit interfaces.
- **Fail-Safe Operations:** Systems default to a safe, non-executing state upon encountering unhandled exceptions or data discrepancies.
- **Decimal Exactness:** Floating-point arithmetic is banned across financial, balance, order, and risk calculations.
- **Data Integrity:** The canonical 1-minute candle is the foundational source of truth from which all higher timeframes and indicators are derived.

## 2. Planned High-Level Modules

### 2.1 CoinDCX Integration
- Encapsulates all transport-level HTTP and WebSocket communication with CoinDCX.
- Manages HMAC-SHA256 request signing, nonce synchronization, and rate-limit credit tracking.
- Normalizes raw exchange responses into strictly typed domain models.

### 2.2 Coin Runtime Layer
- Spawns and manages isolated runtime containers per active instrument (e.g., `BTC-INR`, `ETH-INR`).
- Ensures that issues or crashes in one coin's runtime do not cascade to other coins.
- Dynamically loads instrument configuration (tick size, lot size, margin tiers) discovered from the exchange.

### 2.3 Market Data
- Receives real-time public trade streams, order book snapshots, and ticker updates.
- Employs strict sequence and gap detection to identify missed packets or stale feeds.
- Buffers raw trade ticks for canonical bar synthesis.

### 2.4 Canonical 1m Store
- The definitive, immutable record of 1-minute OHLCV candles persisted to MySQL 8.
- Serves as the single source of truth across backtesting, paper trading, shadow mode, and live execution.
- Bars are finalized authoritatively by Phase 5 using successor-confirmed finality (requiring observation of a valid strictly later minute; wall-clock advance alone never finalizes a candle), gap detection with REST recovery barriers, and strict persist-before-publish guarantees.

### 2.5 Timeframe Aggregation
- Pure mathematical aggregation engine that synthesizes generic higher timeframes (initial production-supported set: 2m, 3m, 4m, 5m, 10m, 15m, 30m, 1h, 4h, 1d) strictly from authoritative Phase 5 canonical closed 1m candles.
- Core architecture is generic for safe integer durations (`Number.isSafeInteger(timeframeMinutes) && timeframeMinutes >= 2`, preserving Phase 5 canonical 1m exclusivity) with UTC Unix-anchored bucket boundaries and exact constituent completeness ($N$ contiguous 1m candles; zero data fabrication or forward-filling).
- Enforces pair-scoped serialized execution across all operations (live processing, startup hydration, and resync) to eliminate race conditions and chronological inversion.
- Controlled by an explicit pair operational state model (`INITIALIZING`, `READY`, `BLOCKED`, `RESYNCING`) gated strictly by Phase 5 eligibility (`state === 'HEALTHY'`, `truthFault === 'NONE'`, `recoveryRequired === false`).
- Employs an isolated 64-bit calculation context and `DerivedAggregateDecimal` bounds (scale $\le 18$, integer $\le 30$, precision $\le 48$) to prevent precision truncation during multi-candle summation.
- Guarantees deterministic live/batch parity: the identical pure aggregation primitive (`aggregateExactBucket`) is executed across live streaming, historical dataset processing, indicator warmup, and backtesting, ensuring byte-equivalent derived market data.
- Reads exclusively from local MySQL `candles_1m` via `Canonical1mRangeReader` with zero external exchange calls and zero higher-timeframe database tables.
- Subordinate to Phase 5 host lifecycle: Phase 6 starts after Phase 5, unsubscribes and stops before Phase 5, and tracks engine-level run ownership to isolate stale async callbacks.

### 2.6 Historical Dataset Engine
- Deterministic, reproducible acquisition, verification, manifest tracking, export, and import of canonical 1-minute historical datasets.
- Reuses the existing read-only `CoinDcxFuturesCandleRestReader` against the public CoinDCX Futures candlestick REST endpoint (`resolution=1`, closed 1m candles only).
- Enforces half-open interval contract `[fromInclusiveMs, toExclusiveMs)` aligned to exact UTC minutes, strictly excluding the forming/current minute.
- Operates a resumable, chunked backfill engine without job-state database tables: derives progress directly from continuous canonical rows in `candles_1m`, fetches only genuine missing spans, and inserts via idempotent repository semantics.
- Enforces a strict zero-fabrication policy: interpolation, forward-filling, previous-close copying, and zero-volume filling are categorically barred. Datasets with unrecoverable exchange gaps fail closed as incomplete.
- Reuses existing immutable MySQL 8 `candles_1m` as the single canonical storage table (`source: 'REST_HISTORICAL'`) under identical `CanonicalDecimal` and structural OHLC validation. Conflict with existing rows fails closed (`CanonicalCandleConflictError`).
- Designated as an offline maintenance/research operation: historical writes must not run concurrently with an active Phase 5 live canonical writer on the same bot/database.
- Establishes deterministic SHA-256 dataset identity: `contentSha256` hashed over ordered canonical logical rows (market truth only, excluding transport metadata) and lowercase 64-character hex `datasetId` hashed over schema, venue, market, pair, range, and content hash.
- Manages dataset manifests (`HistoricalDatasetManifest`) and streaming NDJSON export/import with streaming hash verification for low memory consumption across multi-year datasets.
- Preserves Phase 6 batch/live parity: stores canonical 1m truth only; higher timeframes are derived dynamically via `aggregateExactBucket`.

### 2.7 Indicator Engine
- Deterministic, zero-side-effect computational layer for technical and quantitative indicators (SMA, EMA, Wilder RMA, ATR, RSI, MACD, Bollinger Bands, DMI/ADX, SuperTrend, Donchian Channel, UTC-day VWAP, Volume SMA, Volume Ratio).
- Consumes strictly closed, validated market data truth from Phase 5 `CanonicalCandle1m` (timeframe = 1m) and Phase 6 `HigherTimeframeCandle` via a normalized, read-only `IndicatorCandle` view; does not duplicate candle aggregation.
- Operates within deterministic calculation segments defined by `bootstrapStartOpenTimeMs`; exact recursive indicator state parity across restarts requires replaying continuous closed candles from the identical bootstrap origin (claims that "recent warmup candles" reconstruct recursive state are strictly barred).
- Executes within an isolated 128-digit Decimal calculation context (`IndicatorCalcDecimal`, `ROUND_HALF_UP`) with total prohibition of native floating-point math, providing deterministic headroom for Bollinger squared sums (up to 77 digits) and VWAP price-volume accumulations (up to 88 digits).
- Strictly prevents internal state contamination: recursive indicator states retain full 128-digit precision and never feed rounded 18dp public outputs back into recursive state machines.
- Enforces strict prefix determinism (zero lookahead): indicator output for candle $t$ depends strictly on candles $\le t$ within the calculation segment; future candles never alter past results; centered windows and retroactive repainting are barred.
- Guarantees exact batch/incremental parity: batch computations feed the identical sequential state kernel as live incremental processing; batch results equal incremental results timestamp-by-timestamp across all supported indicators.
- Employs deterministic warmup alignment: emits explicit `value: null` (never `0`, `NaN`, `Infinity`, or fake seeds) until mathematical warmup conditions are met.
- Enforces runtime safety on UTC-day VWAP: requires `floor(openTimeMs / 86_400_000) === floor((closeTimeExclusiveMs - 1) / 86_400_000)`, failing closed on candles genuinely straddling UTC midnight without synthetic splitting or open-day attribution.
- Enforces universal parameter boundary $1 \le period \le 100\,000$ (`MAX_INDICATOR_PERIOD`) and bounded memory guarantees ($O(period)$ for rolling indicators, $O(1)$ for recursive state machines).
- Maintains complete state isolation per instrument pair, timeframe, indicator type, parameter set, and bootstrap origin with zero module-global mutable state; multi-timeframe strategies combine independent indicator instances.
- Zero indicator database persistence: indicators are pure derived mathematical transformations; restart and recovery replay closed warmup candles from the segment origin.
- Explicitly defers true Volume Profile pending canonical trade-level price-volume data; synthetic intrabar volume distribution heuristics across OHLCV candles are strictly prohibited.
- Complete mathematical specifications, recurrence relations, precision budgets, and verification fixtures are frozen in `docs/INDICATOR_ENGINE.md`.

### 2.8 Strategy Framework (Phase 10)
- Environment-neutral, deterministic quantitative strategy architecture where the **identical pure strategy kernel** executes across historical backtesting, paper trading, shadow evaluation, and live production trading without environment-specific branches.
- Enforces strict unidirectional dependency, fail-closed input validation, and auditable dispatch:
  $$\text{Closed Market Truth} \longrightarrow \text{Phase 8 Indicator Kernels} \longrightarrow \text{Sanitized StrategyEvaluationSnapshot} \longrightarrow \text{Pure Strategy Kernel} \longrightarrow \text{StrategyDecision} \longrightarrow \text{StrategyDecisionSink} \longrightarrow \text{Environment Adapter} \longrightarrow \text{Dispatch Audit} \longrightarrow \text{Downstream Actions}$$
- **Zero Account / Order Awareness in Strategy Core:** The pure strategy core (`src/strategies/core/**`) is strictly prohibited from importing backtest engines, exchange clients, order APIs, risk engines, account equity, cash balances, exchange positions, or active orders.
- **Pre-Strategy Input Validation Contract:** Enforces strict structural checks (alias presence, pair match, timeframe match, closed timestamps, trigger freshness, and HTF same-timestamp freshness) and null-regression detection before warmup/ready handling. Malformed or missing indicator truth fails closed and never silently becomes warmup or flat.
- **Mandatory Decision Audit Sink:** Every actual trigger evaluation writes an immutable `StrategyDecision` to `StrategyDecisionSink` before any environment adapter reconciliation occurs. If the sink fails, the adapter fails closed with zero order output.
- **Environment Adapters Sanitize & Reconcile:** Adapters (e.g. `StrategyBacktestParticipantAdapter`) sanitize incoming runtime context (explicitly stripping account, position, and open-order fields) into an immutable `StrategyEvaluationSnapshot`, call `kernel.evaluate(snapshot)`, record a `StrategyDecisionDispatchRecord`, and reconcile abstract target exposures with environment-specific execution mechanisms.
- **Discriminated Non-Actionable Warmup:** Legitimate indicator warmup emits `status: 'WARMING'` with `targetExposure = null`; converting warmup into `FLAT` or generating exit orders during warmup is strictly prohibited, preventing accidental position liquidation during bootstrap.
- **Abstract Target Exposure:** Pure strategies emit desired market direction (`LONG`, `SHORT`, `FLAT`), never concrete orders (`BUY`, `SELL`), order types (`MARKET`, `LIMIT`), quantities, or leverage.
- **Trigger-Timeframe Scheduling:** Strategies evaluate if and only if their configured `triggerTimeframeMinutes` candle closes at evaluation timestamp $T$; multi-timeframe strategies observe newly finalized higher-timeframe candles and indicators closing at $T$ in ascending order, or their latest prior closed values.
- **Deterministic Identity & Canonical Normalization:** Exact decimal parameter canonicalization normalizes numeric-equivalent values (`"2"`, `"2.0"`, `"002.000"` $\to$ `"2"`) before SHA-256 `parameterHash` computation; analytical run segments bind authoritative per-timeframe `indicatorBootstrapIdentity` entries into `strategyInstanceId`; and adapter-only `fixedResearchQuantity` binds Phase 9 participant and run identity without leaking into strategy parameter hash.
- **Isolated Decimal Arithmetic:** Threshold and breakout math evaluates within an isolated 128-digit Decimal context (`StrategyCalcDecimal`, `ROUND_HALF_UP`) with native floating-point math strictly prohibited.
- **First 4 Parameterized Strategies:** Core implementations for EMA Trend V1 (`EMA_TREND`), ATR Breakout V1 (`ATR_BREAKOUT`), RSI Momentum V1 (`RSI_MOMENTUM`), and Multi-Timeframe Trend V1 (`MULTI_TIMEFRAME_TREND`).
- Complete specifications and verification contracts are frozen in `docs/STRATEGY_FRAMEWORK.md`.

### 2.9 Backtesting Engine
- High-performance, strictly deterministic offline event replay and simulation environment operating on verified Phase 7 canonical 1m datasets.
- Cryptographically bound dataset ingestion via a two-pass contract: Pass 1 verifies the complete manifest range `[fromInclusiveMs, toExclusiveMs)` against Phase 7 canonical logical-row hashing primitives (`encodeHistoricalLogicalRow`, `canonicalHashDecimal`, `computeDatasetId`); Pass 2 streams the replay span `[bootstrapFromInclusiveMs, replayToExclusiveMs)` from the identical immutable source. A valid manifest paired with a substituted candle stream is never accepted.
- Reuses Phase 6 `aggregateExactBucket` as the sole higher-timeframe aggregation primitive with common bootstrap alignment across all configured HTFs, and Phase 8 `IndicatorKernel` instances bound to actual derived candle origins, maintaining strict batch/incremental parity.
- Enforces strict no-lookahead causality: evaluation at timestamp $T$ observes only market data closed by $T$; decisions at $T$ become eligible for simulated execution no earlier than the next canonical source bar opening at $T$; order cancellations accepted at $T$ take effect at the next bar open before any fills, winning against open gap-throughs.
- Implements conservative 1m OHLCV execution semantics: all-or-none fills with zero synthetic partial-fill or queue priority fabrication; strictly positive execution prices ($> 0$); raw `bar.OPEN` post-only marketability rejection barrier; strict price penetration for resting `POST_ONLY_LIMIT` orders (`bar.low < limitPrice` for BUY, `bar.high > limitPrice` for SELL; equality touches do not fill); gap-through reference pricing for `STOP_MARKET` orders; intrabar OCO ambiguity resolved via `ADVERSE_FIRST` candidate reduction merged into a global `orderSequence` ascending total order; and whole-order rejection for reduce-only excess.
- Evaluates within an isolated 128-digit Decimal calculation context (`BacktestCalcDecimal`, `ROUND_HALF_UP`) with public 18-decimal quantization (`BacktestDecimal`) and linear perpetual futures accounting using discovered instrument metadata constraints (`priceIncrement`, `quantityIncrement`, `minQuantity`, `minTradeSize`, `minNotional`, and `contractMultiplier`).
- Exact reversal accounting: realized PnL is computed strictly on closing quantity ($\min(Q_{\text{existing}}, Q_{\text{fill}})$), the opening remainder generates zero realized PnL at entry, and exactly one trading fee is assessed on total executed notional.
- Deterministic accounting ledger: maintains `netPnl = realizedGrossPnl + unrealizedGrossPnl + fundingPnl - totalFees` and `equity = initialEquity + netPnl`; embedded spread and slippage cost attributions are tracked for reporting without double-counting.
- Causal funding cash flows: funding schedules are bounded to `(bootstrapFromInclusiveMs, replayToExclusiveMs]`; exactly one `FUNDING_APPLIED` event is emitted per scheduled timestamp (even when flat) and applies strictly to positions surviving through bar close at $T$ before evaluation at $T$.
- Guaranteed terminal disclosure: unresolved active orders are preserved in `terminalOpenOrders` and terminal open positions are marked at the final closed candle without synthetic liquidation, fake fees, or fake cancellations.
- Resource bounds & immutable snapshots: all behavior-affecting inputs are defensively normalized and deeply frozen before `runId` computation; `maxOpenOrders` (default 20, ceiling 100) enters run manifest identity; core replay memory is bounded to $O(\text{working state})$ decoupled from pluggable event sinks; and event sink write failures fail closed immediately (`isValid = false`, terminal `FAILED`).
- Auditable cryptographic lineage: deterministic JSON serialization with recursive key sorting at every nesting depth, newline-framed event ledger hashing (`eventLedgerSha256`), and comprehensive result hashing (`resultSha256`).
- Preserves strategy boundaries: pure Phase 10 strategies emit abstract signals through standardized interfaces; Phase 9 executes orders through research orchestration adapters without backtest-specific state leakage or live side effects.

### 2.10 Strategy × Coin Matrix Research Engine (Phase 11)
- Authoritative research orchestration engine systematically exploring multi-coin, multi-strategy, multi-parameter quantitative hypothesis spaces.
- Enforces the deterministic research pipeline:
  $$\text{Phase 7 Dataset} \longrightarrow \text{Phase 8 Indicators} \longrightarrow \text{Phase 10 Strategy} \longrightarrow \text{Phase 9 Deterministic Backtest} \longrightarrow \text{Phase 11 Matrix Orchestration} \longrightarrow \text{Raw Research Matrix Evidence} \longrightarrow \text{Phase 12 Validation}$$
- **Predeclared Finite Candidate Space:** Evaluates strictly finite parameter grids and candidate lists. No adaptive mutation, Bayesian optimization, genetic algorithms, or future-result-driven candidate generation.
- **Input-Side Defensive Immutability:** Defensively deep-copies and deep-freezes all caller-supplied parameter arrays, candidate space maps, and configuration objects upon ingestion, guaranteeing that post-construction caller mutations cannot alter plan contents, `matrixPlanId`, cell definitions, or execution results.
- **Phase 10 Validation Authority:** Reuses Phase 10 `StrategyDefinition.normalizeParameters` as the sole parameter validation authority. Zero duplicated parameter validator code; invalid parameter combinations fail closed immediately before backtest execution.
- **Explicit Duplicate Rejection:** Canonical parameter normalization converts numeric equivalents (e.g. `"2.0"` $\to$ `"2"`); logical collisions fail closed with structured duplicate parameter errors rather than silently producing duplicate cells.
- **Cryptographic Dataset & Window Binding:** Every pair explicitly binds to an immutable Phase 7 `datasetId` and `contentSha256` covering both indicator warmup (`bootstrapFromInclusiveMs`) and the active research window (`evaluationFromInclusiveMs` to `evaluationToExclusiveMs`); auto-picked datasets or coverage gaps fail closed.
- **Versioned Indicator Bootstrap Policy:** Binds frozen `bootstrapPolicyId` (`P11_INDICATOR_BOOTSTRAP_V1` supporting EMA, ATR, RSI with exact $3 \times period$ lookback); any unsupported indicator type (SMA, MACD, Bollinger, SuperTrend) fails closed immediately before plan finalization or execution without heuristic guessing. Computes common bootstrap alignment across all required timeframes, deterministically generating the authoritative Phase 10 `indicatorBootstrapIdentity` and `strategyInstanceId`.
- **Verified Clean Git Source Identity:** Enforces full commit OID auto-capture (`git rev-parse HEAD`) and strict working-tree cleanliness (`git status --porcelain=v1 --untracked-files=all` must be empty). Dirty working trees, staged changes, untracked non-ignored files, missing Git metadata, or prebuilt plan commit mismatches fail closed; source state invariance is validated at execution boundaries.
- **Authoritative Phase 9 Manifest & RunId Path:** Directly invokes the real Phase 9 `normalizeBacktestInputs` and `sha256CanonicalJson` with `configuredTimeframes` derived from kernel indicator requirements (distinct $TF > 1$, sorted ascending, 1 excluded). Binds common run inputs via `MatrixBacktestExecutionConfig` and pair-specific funding schedules via `fundingScheduleBinding`, with runtime resources verified against plan bindings before execution.
- **Absolute Phase 9 Parity:** Every matrix cell executes through the genuine Phase 9 `BacktestEngine` and Phase 10 `StrategyKernel` via `StrategyBacktestParticipantAdapter`. Specialized, simplified, or "fast" research mocks are strictly prohibited.
- **Cryptographic Plan & Cell Lineage:** Produces deterministic SHA-256 `matrixPlanId` over normalized canonical plan bytes, `matrixCellId` over canonical cell identity payload, and expected Phase 9 `runId` binding `fixedResearchQuantity`.
- **Canonical Cell Ordering & Concurrency Determinism:** Cells are ordered by `pair` $\to$ `strategyId` $\to$ `strategyVersion` $\to$ `parameterHash` $\to$ `strategyInstanceId` $\to$ `expectedRunId`. Multi-worker parallel execution yields bit-for-bit identical ordered results and `matrixResultSha256` independent of completion timing, with all wall-clock durations and timing metadata strictly eliminated from canonical artifacts.
- **Discriminated Results & Fail-Closed Audit Accounting:** Terminal cell results follow a strict discriminated union (`MatrixCellCompletedResult` with genuine `BacktestRunResult` vs `MatrixCellFailedResult` with `MatrixCellFailure`; pre-engine failures record `outcome: null` and `runId: null` without fabricated Phase 9 outcomes). Failed cells never silently disappear. If any cell fails, the matrix reports `PARTIAL` or `FAILED`, preserving all planned cell records in the evidence ledger. Mid-run Git tree changes mark the matrix and pending cells `FAILED`.
- **Phase 9 Cache Verification:** Cache hits require exact `runId` and `matrixCellId` match and verification via `sha256CanonicalJson(outcome without resultSha256) === resultSha256`. Failed outcomes are never reusable cache hits.
- **Strict Anti-Scope & Zero Production Mutation:** Phase 11 produces raw, read-only research evidence. It never selects winners, computes statistical rankings, or promotes strategies to paper/live trading. Cross-coin raw PnL is not directly comparable without downstream capital normalization.
- Complete specifications and verification contracts are frozen in `docs/STRATEGY_COIN_MATRIX.md`.

### 2.11 Research Validation Lab (Phase 12)
- Authoritative statistical validation subsystem evaluating the empirical robustness and overfitting resistance of quantitative hypothesis candidates generated by Phase 11.
- Enforces the deterministic validation pipeline:
  $$\text{Phase 11 Candidates} \longrightarrow \text{Walk-Forward Folds (IS/OOS)} \longrightarrow \text{Phase 9 Event Capture} \longrightarrow \text{Robustness Engines} \longrightarrow \text{Cost Stress / Monte Carlo / DSR} \longrightarrow \text{Policy Verdict}$$
- **Cryptographic Validation Plan Identity:** Binds all validation parameters, datasets, temporal windows, walk-forward parameters, holdout boundaries, cost stress models, Monte Carlo policies, and approval thresholds into a deterministic SHA-256 `validationPlanId`.
- **Invariant Cross-Fold Subject Identity:** Defines `validationSubjectId = sha256CanonicalJson({ pair, strategyId, strategyVersion, parameterHash })`, preserving subject continuity across folds while avoiding fragmentation caused by fold-varying `strategyInstanceId`.
- **Chronological Walk-Forward Validation:** Employs `P12_WALK_FORWARD_V1` with safe-integer UTC day-aligned boundaries and contiguous, non-overlapping out-of-sample (OOS) test windows ($\text{stepDays} === \text{testDays}$). Solves $K = \max\{j \ge 1 \mid \text{OOS\_end}(j-1) \le \text{holdoutStartMs}\}$ and canonically records any unused calendar tail. Prohibits random train/test row splits and lookahead leakage.
- **Isolated Final Holdout & Operator Attestation:** Freezes a final holdout window chronologically after all walk-forward development folds, governed by explicit operator attestation (`holdoutExposureDeclaration: 'UNSEEN_BY_OPERATOR' | 'PREVIOUSLY_OBSERVED'`) rather than false cryptographic claims of historical data freshness. Modifying candidate spaces or policies generates a new `validationPlanId` and invalidates prior holdout claims (zero silent holdout reuse).
- **Zero Simulator Duplication & Mandatory Fresh Execution:** Captures streaming evidence directly from the genuine Phase 11 `executeCell` $\to$ Phase 9 `BacktestEngine` execution path via an execution-only `eventSinkFactory` seam without altering Phase 11/Phase 9 identities or reconstructing candle PnL. Public Phase 12 dependencies structurally omit cache parameters, calling Phase 11 with `cache: undefined` and asserting fresh collector completion; any cell reporting `COMPLETED` without freshly finalized collector evidence fails closed (`EVIDENCE_INTEGRITY_FAILURE`).
- **Independent Event Ledger Hashing:** The collector independently hashes every observed event using Phase 9's canonical event hasher in strict monotonic sequence, finalizes after `BacktestEngine.run()` returns, and asserts `observedEventLedgerSha256 === outcome.eventLedgerSha256` before deriving `validationEvidenceSha256`.
- **Analysis Window & Funding-Edge Sampling:** Baseline equity $E_0$ is captured at `analysisStartMs` post-funding flush; metrics evaluate strictly over $\text{analysisStartMs} < T \le \text{analysisEndExclusiveMs}$, capturing the terminal candle close and funding settlement at `analysisEndExclusiveMs`. Terminal equity is sampled strictly at UTC midnight boundaries ($t \pmod{86\,400\,000} === 0$), yielding $N$ daily returns from $N+1$ boundary equity snapshots ($E_0 \dots E_N$).
- **128-Digit Decimal Financial Metrics:** Evaluates daily net returns, minute-close maximum drawdown, per-day Sharpe and Sortino (annualized via $\sqrt{365}$), and expectancy/profit factors using isolated high-precision Decimal arithmetic, prohibiting native JavaScript floats, `parseFloat`, and `Math.random`. Compound annualized return is excluded from V1 canonical evidence.
- **Strict Metric Validity Discriminated Union:** Every metric terminates in `VALUE`, `UNDEFINED`, or `INSUFFICIENT_DATA` (zero `NaN` or `Infinity`). Differentiates gross trade-level metrics (`grossTradeProfitFactor`, `grossTradeExpectancy`) from cost-inclusive net daily metrics (`netDailyProfitFactor`, `netDailyExpectancy`).
- **Real Phase 9 Cost Stress Testing:** Re-evaluates candidates across deterministic cost stress scenarios (`MODERATE_STRESS`, `SEVERE_STRESS`) by dispatching genuine Phase 9 backtest runs with distinct run IDs and authentic fills, strictly barring post-hoc synthetic fee deductions.
- **Deterministic Monte Carlo Permutations:** Evaluates daily return path risk via `P12_MONTE_CARLO_PERMUTATION_V1`, employing a counter-mode CSPRNG stream seeded canonically via HMAC-SHA256 from plan, subject, fold, and policy IDs to execute an unbiased Fisher-Yates shuffle.
- **Statistical Overfitting Control:** Implements the Deflated Sharpe Ratio (DSR) evaluated over aggregate OOS daily returns in per-day units with an exact $M === 1$ branch ($SR_0 = 0$), penalizing trial count $M$, return skewness, and kurtosis, combined with IS $\to$ OOS degradation and fold pass ratio consistency gates.
- **Generic Parameter Neighborhood Stability:** Evaluates parameter plateau stability and detects fragile "cliff" anomalies using generic candidate space topology without strategy-specific hardcoding.
- **Strict Non-Ranking & Read-Only Governance:** Emits immutable read-only gate evaluations terminating in a discrete verdict following strict precedence (`FAILED` > `INSUFFICIENT_EVIDENCE` > `PASSED`). Never computes rankings, composite scores, leaderboards, or capital allocations, and never mutates production Coin Runtime state (Phase 15 owns ranking).
- Complete specifications and verification contracts are frozen in `docs/RESEARCH_VALIDATION.md`.

### 2.12 Risk & Leverage Engine (Phase 13)
- The non-bypassable, pure, deterministic guardian standing between the genuine Phase 10 `StrategyDecision` and any future execution intent: `evaluateRisk(RiskEvaluationContext): RiskDecision` performs zero I/O, zero persistence, and constructs no order — Phase 13 never produces an `ExecutionIntent`, and never pretends `InstrumentSelectionDecision` (not yet built) already exists.
- **Real StrategyDecision Lineage:** Phase 13 binds to the verbatim Phase 10 `StrategyDecision` contract (`decisionId`, `decisionSequence`, `strategyInstanceId`, `strategyId`, `strategyVersion`, `parameterHash`, `pair`, `evaluationTimeMs`, `triggerTimeframeMinutes`, `status`, `targetExposure`, `reasonCodes`) — it carries no price, leverage, or quantity, and Phase 13 never assumes otherwise. `decisionId` is independently recomputed via the genuine kernel hash formula before use; `status = 'WARMING'` is a structural no-op (no candidate, no decision); entry/stop/leverage are separately versioned, provenance-bound proposals supplied by a distinct upstream bridge; `side`/`action` (`OPEN`/`CLOSE`/`NO_CHANGE`/`REVERSAL_DEFERRED`) are derived deterministically from `targetExposure` plus authoritative current position truth — there is no partial-reduce or reversal-in-one-step path, since no input contract supplies a target quantity.
- **Frozen Field-by-Field Authority Matrix:** Rather than a single blanket "pointwise min," every decision-affecting field (risk-per-trade, max leverage, max quantity, max notional, global/pair/strategy exposure, max concurrent positions, daily loss, drawdown) has an explicit per-layer classification — `PROPOSE`, `TIGHTEN`, `HARD_CAP`, or `NOT_APPLICABLE` — across global config, pair config, strategy proposal, risk mode, per-trade override, exchange/tier authority, and account/exposure gating. `NOT_APPLICABLE` never becomes `Infinity`; every `TIGHTEN` relationship is enforced once at configuration load time, so `HIGH`/`CUSTOM` structurally cannot widen any hard cap (Invariant 11).
- **Conservative Risk-Budget Position Sizing → Finite Leverage-Tier Enumeration:** Quantity is first capped by a risk-budget ceiling (`currentEquityInr × riskPerTradePercent` ÷ stop distance, isolated 128-digit `RiskCalcDecimal`, `ROUND_HALF_UP`, floor-only rounding). Leverage and final quantity are then resolved by exhaustively enumerating every CoinDCX leverage tier exactly once (a single finite pass bounded by tier count, replacing an earlier flawed fixed-point loop) and selecting the greatest feasible quantity across all tiers — never a locally-stable-but-suboptimal answer. The result is a first-class `PositionSizingDecision`, which `RiskDecision` wraps unchanged after adding exposure/loss/drawdown gates.
- **Genuine, Freshness-Gated CoinDCX Dynamic Tier Consumption:** Leverage and margin data is consumed exclusively through a normalized `CoinDcxLeverageTierSnapshot` bound to the real Phase 2 read-layer `InrFuturesInstrument.dynamicPositionLeverageTiers` / `dynamicSafetyMarginTiers` models, carrying an explicit `semanticsStatus` (`VERIFIED` / `SEMANTICS_UNVERIFIED`) since CoinDCX's tier-boundary inclusivity is not yet documented — new exposure fails closed while unverified. Freshness is policy-owned (never snapshot-declared) and compared only against `RiskEvaluationContext.evaluationTimeMs`, never a wall clock inside the pure engine.
- **Initial Margin Only — Maintenance Margin Explicitly Deferred:** `estimatedInitialMarginUsdt`/`estimatedInitialMarginInr` (`notional ÷ finalLeverage`) are initial-margin estimates only; Phase 13 does not compute maintenance margin or a liquidation price absent authoritative confirmation of CoinDCX's progressive tranche semantics — `dynamicSafetyMarginTiers` are retained as disclosed evidence only.
- **Discriminated `RiskDecision`:** `AcceptedOpenRiskDecision | AcceptedCloseRiskDecision | RejectedRiskDecision` — each accepted action has its own complete, non-overlapping field shape (`CLOSE` never carries a fabricated leverage/margin figure it never computed); a rejection structurally cannot carry approved financial values (`approved: null`) and always carries a `primaryReasonCode` plus ordered `secondaryReasonCodes`; every applied cap uses an explicit `RESOLVED` / `NOT_APPLICABLE` / `UNRESOLVED` value rather than a fabricated zero. For `OPEN`, the accepted `approved` envelope is a pure, value-preserving **projection** of the authoritative `PositionSizingDecision.sizing` record — a frozen seven-field rename-only mapping (`finalQuantity` → `approvedQuantity`, and so on), never a structural duplicate of it: the calculation record keeps its intermediate derivations, the approval carries only execution-facing values, no number is recomputed on the way across, and the approval is cryptographically bound to the sizing record it projects.
- **Strategy-Instance Ownership Gates Both `OPEN` and `CLOSE`, With Complete Identity:** Same-pair exposure attribution for exposure *limits* is `strategyId`-keyed (a legitimate strategy-level aggregate), but ownership of a specific position or reservation is validated against the **complete** four-field identity tuple (`strategyInstanceId` + `strategyId` + `strategyVersion` + `parameterHash`) — never `strategyInstanceId` alone, closing a residual gap where a `strategyInstanceId` match with a mismatched strategy configuration would otherwise be trusted. Each per-instance record carries current quantity **and** current notional. Ownership is represented as a discriminated `ReconciledFlatOwnership | ReconciledOpenOwnership | UNRECONCILED` union — a flat pair carries `positionId: null` (never a fabricated placeholder), while an open position requires a genuine, non-empty CoinDCX `positionId`. One strategy definition's second instance can never close another instance's share, and an exchange-aggregated position with no proven per-instance breakdown (or one whose reported quantities fail to sum to the authoritative aggregate) is treated as `UNRECONCILED` and fails closed for **both** `OPEN` (new exposure may already belong to another instance) and `CLOSE` rather than guessing. Current-notional reconciliation is equally deterministic and is **not** delegated to adapter discretion: because CoinDCX exposes no authoritative position notional, the aggregate is derived by one frozen, policy-versioned method — mark price × contract multiplier × settlement conversion rate, quantized once into a shared per-unit valuation factor, then multiplied by quantity — so every instance and the aggregate share one valuation basis (never entry price for one and mark price for another) and reconcile under **exact** canonical-Decimal equality with no tolerance. The engine recomputes rather than trusts, so a caller- or adapter-supplied aggregate notional cannot bypass reconciliation; a position whose mark price is unavailable is `UNRECONCILED` rather than valued at a substituted price. **Sign semantics are frozen at a single boundary:** CoinDCX's signed `activePositionQuantity` is normalized exactly once into a `positionDirection` label plus a strictly-positive `quantityMagnitude`, after which no signed quantity exists anywhere in ownership reconciliation. Every per-instance quantity is a strictly-positive magnitude (a zero share is represented by omitting the record, never by a `"0"` entry), direction is inherited from the authoritative open position and is never encoded in a quantity's sign, and an instance therefore cannot represent the opposite direction inside the same one-way position — so a mixed-sign set such as `+2` and `-1` can no longer cancel into a falsely reconciling aggregate of `1`.
- **Finite Tier Enumeration Applies Every Notional Cap:** The tier-candidate intersection explicitly includes the instrument's own `maxNotional`, the resolved max-notional-per-trade cap, and remaining exposure headroom — not just margin and the risk-budget ceiling — and tier intervals are now adapter-verified explicit bounds (`lowerNotionalUsdt`/`upperNotionalUsdt`/inclusivity), never derived by Phase 13 from raw tier caps.
- **Strict, Zero-Tolerance Temporal Causality and Expected Source Authority:** The pure engine enforces `sourceTimeMs ≤ observedAtMs ≤ evaluationTimeMs` with no clock-skew allowance of its own — any operational skew tolerance is strictly an adapter-side concern applied before a snapshot is ever constructed. Position identity (`positionId`, bound to the genuine Phase 2 `InrFuturesPosition.id`) prevents stale ownership data from a closed-and-reopened position being silently reapplied. Every snapshot's `sourceId` is additionally checked against a policy-owned `RiskSourceAuthorityPolicy` — never a value the evidence itself can assert — so a snapshot can never self-certify its own trust anchor.
- **Direct-INR Daily Loss Gate:** The primary daily-loss circuit breaker compares a non-negative loss magnitude (`max(0, -netDailyPnlInr)`) directly against a resolved INR cap (`min(globalMaxDailyLossInr, maxDailyLossInr)`, both required `> 0`) — never via a percentage detour. An optional percentage-of-equity gate may additionally be configured, but fires its own distinct reason and never substitutes for the INR gate.
- **One Rejection Taxonomy, One Global Precedence Table:** A declared `decisionId` or `contentSha256` that differs from canonical identity/hash recomputation yields `DECISION_IDENTITY_MISMATCH` (a rejected decision), never `RISK_SOURCE_INVALID` (a thrown config/programming error) — `RISK_SOURCE_INVALID` is reserved strictly for input whose missing/unknown fields, invalid types, or unparseable, non-finite, or prohibited non-canonical Decimal forms prevent canonical identity from being established at all (per the ingestion/normalization distinction in the risk spec §11.1) — including valuation evidence, where a well-formed object whose bound multiplier, conversion rate, or valuation-method version merely disagrees with the surrounding evidence is a deterministic Group B rejection (`VALUATION_METHOD_MISMATCH`, `PAIR_STATE_UNAVAILABLE`, or `SETTLEMENT_RATE_UNAVAILABLE` as applicable), never a thrown error — as is a valuation whose inputs are each individually valid but whose arithmetic cannot be completed within the frozen decimal context (`VALUATION_NUMERIC_CONTEXT_EXCEEDED`). After canonical identity is established, `RISK_SOURCE_INVALID` is unreachable. A policy-owned expected `sourceId` differing from actual `sourceId` yields `SOURCE_ID_MISMATCH`; this is checked separately from content-hash equality. A completed valuation amount differing from the reported amount yields `POSITION_OWNERSHIP_UNRECONCILED`. Identity codes are correspondingly narrow: `DECISION_IDENTITY_MISMATCH` covers identity and hash recomputation only, never numeric value reconciliation, which belongs to the code owning that reconciliation. Temporal failures are likewise split by cause rather than by snapshot type: any breach of `sourceTimeMs ≤ observedAtMs ≤ evaluationTimeMs` — settlement conversion evidence included — is `EVIDENCE_TEMPORAL_CAUSALITY_VIOLATION`, while the per-snapshot `*_STALE` codes are reserved exclusively for causally valid evidence that is merely older than its policy age limit. A frozen 13-step evaluation pipeline determines *when* each check runs, but final reason ordering — including multiple reasons discovered within a single step — is decided exclusively by index into one canonical, self-validating `REJECTION_PRECEDENCE_V1` table (every known rejection code exactly once), never by incidental object/array/Map/Set iteration order.
- **Adapter Boundaries Are Interface-Only:** `AccountRiskStateProvider` (equity/drawdown/daily-PnL — genuinely not supplied by the existing CoinDCX wallet model) and a settlement conversion provider (USDT→INR, bound to an explicit market/symbol identity, not currencies alone — genuinely unimplemented in Phase 2) are frozen as contracts Phase 13 consumes, not adapters Phase 13 builds.
- **A Decision Is Not Valid Forever:** An `ACCEPTED` `RiskDecision` is scoped to the exact snapshots and `evaluationTimeMs` bound into its identity; later phases (17/18) must revalidate all decision-affecting state before any external mutation — Phase 13 itself remains side-effect free and defines no expiry mechanism.
- **Deterministic Identity & Replay:** `riskDecisionId`/`positionSizingDecisionId` are computed via the repository's single canonical-JSON SHA-256 hasher (`sha256CanonicalJson`, reused from Phase 9/11/12) over frozen policy identities and independently-computed content hashes of every snapshot, with canonical Decimal normalization (`"1"`/`"1.0"`/`"1.000"` hash identically) and exact-shape ingestion (no unknown field silently enters or escapes identity) — strictly excluding wall-clock reads, host/PID/worker identifiers, and mutable object ordering. Every policy layer capable of changing an outcome is bound into `riskPolicyId` — including the freshness thresholds, via `riskFreshnessPolicyId`, so that tightening or loosening any snapshot max-age necessarily changes every downstream decision identity rather than silently altering results under an unchanged one.
- Complete specification and verification contracts are frozen in `docs/RISK_LEVERAGE_ENGINE.md`.

### 2.13 Paper Trading & Shadow Mode

### 2.14 Execution Engine
- State machine managing the lifecycle of an order: `INTENT_CREATED` → `SUBMITTED` → `ACKNOWLEDGED` → `PARTIALLY_FILLED` → `FILLED` / `CANCELLED` / `REJECTED`.
- Handles intelligent order routing, post-only enforcement, and partial fill tracking.
- Realized by Phase 17 (section 2.20), with one deliberate deviation from the original sketch: post-only is NOT enforced, because the verified CoinDCX futures order contract does not establish a maker-only guarantee. Phase 17 models it as an explicitly unsupported semantic and rejects an intent that requires it, rather than degrading it into a taker order.

### 2.15 Reconciliation & Crash Recovery
- Runs immediately on startup before any trading loops begin.
- Fetches ground-truth exchange positions, open orders, and balances from CoinDCX.
- Resolves inconsistencies between local database state and exchange state; cancels dangling orphan orders.
- Realized by Phase 18 (section 2.21), with two deliberate deviations from the original sketch: orphan cancellation is **disabled by default** rather than automatic, because cancelling an order the system cannot account for is the most dangerous action available to it; and "resolves inconsistencies" is narrowed to *reconstructs only where exactly one result is provable* — a genuine economic conflict is persisted as a durable fault and blocks trading, never silently repaired to match the exchange.

### 2.19 Strategy Ranking (Phase 15)
- Deterministic, strictly analytical Strategy x Coin ranking (`P15_RANKING_V1`) consuming only genuine Phase 12 `PASSED` evidence and emitting read-only ordinal evidence. It places no order, mutates no Phase 14 account state, changes no Phase 13 risk admission, and promotes no coin runtime lifecycle.
- **Reused Input Authority:** A candidate enters a ranked universe only through the existing Phase 12 `issueResearchApprovalOrigin` genuine-origin check; `FAILED`, `INSUFFICIENT_EVIDENCE`, forged and structurally-cloned plan results are all refused by that same call. Metric values are read from the same genuine deep-frozen `StrategyValidationRecord`, never from a caller-supplied DTO, so a coordinated metric + hash substitution has nothing to substitute into.
- **One Frozen Policy:** Metric set and Phase 12 sources, weights (Sharpe 25%, Sortino 15%, max drawdown 20%, net daily profit factor 15%, net daily expectancy 10%, OOS fold pass ratio 10%, parameter neighbourhood sensitivity 5%), per-metric direction, normalization algorithm, tie-break precedence, Decimal semantics and the frozen Phase 14 economic limitation are bound into `rankingPolicyId = sha256CanonicalJson(P15_RANKING_V1)` and self-validated at module load.
- **Candidate-Set-Relative Ordinal Normalization:** No invented absolute financial ceiling. Distinct canonical values are ordered best to worst by exact 128-digit Decimal comparison (ORDER inverted, never the numeric sign, for lower-is-better metrics), given a dense ordinal position, and mapped to `[0, 1]`; quantized weighted terms re-add to the published composite with no residue.
- **Pair-Local Leaderboards:** Each pair is an independent run with its own `rankingRunId`; there is no cross-coin ordinal comparison in V1, so no capital or regime comparability is assumed.
- **Fail-Closed Validity & Deterministic Ties:** A required metric that is absent, `UNDEFINED`, `INSUFFICIENT_DATA` or non-canonical yields `INSUFFICIENT_RANKING_EVIDENCE`, never a coerced zero or a silent re-weighting. Composite ties resolve through one frozen total order (lower max drawdown, higher Sharpe, higher Sortino, higher profit factor, lexical `validationSubjectId`) with zero wall-clock, insertion-order, worker or random input.
- **Deterministic Identity & Immutable Persistence:** `rankingRunId` binds the policy, the pair, the Phase 12 `validationPlanId` (transitively binding the verified-clean source commit) and the exact candidate universe including each candidate's canonical component values. Additive immutable `ranking_run`/`ranking_result` tables are keyed by those deterministic identities, so re-running the same semantic ranking is idempotent and a same-id/different-content write fails closed.
- **Promotion Firewall:** Every result is permanently `economicStatus = FUNDING_EXCLUDED`, `promotionEligible = false`, `maxLifecycle = PAPER`. Funding-excluded paper economics are modelled only as separate, explicitly-labelled non-authoritative observation metadata attached AFTER the ranking is sealed, so paper PnL provably cannot affect a composite score, a rank, or a ranking identity.
- Complete specification and verification contracts are frozen in `docs/STRATEGY_RANKING.md`.

### 2.20 CoinDCX Live Execution (Phase 17)
- The first mutation-capable exchange path in the system: it converts an already-authorized execution request into authenticated CoinDCX futures order operations (create, cancel, and observation through the documented list-orders endpoint). Live mutation is **disabled by default** and cannot be switched on by a call-site flag — only by an explicit production configuration that additionally requires `NODE_ENV=production`, non-empty credentials, and a non-empty account and pair allowlist.
- **Ports and adapters:** `src/execution/live/**` owns the `CoinDcxFuturesOrderGateway` port, the state machine, the authority model and the persistence port, and reaches **no** integration module at all — preserving and strengthening the Phase 14 lint-enforced execution/integration boundary. The mutation-capable adapter and the single approved production root live under `src/integration/coindcx/live/`, alongside (but strictly isolated from) the frozen Phase 2 read-only client, which gains no order method.
- **One mutation boundary:** `production-runtime.ts → order-gateway.ts → mutation-transport.ts → signer.ts / node:http(s)` is the only approved authenticated order-mutation chain. Only `mutation-transport.ts` directly owns outbound network mutation; only `order-gateway.ts` directly imports it; only `production-runtime.ts` imports the gateway. A TypeScript-AST graph follows imports, re-exports, dynamic import, CommonJS require aliases, `module.require`, and `createRequire`; unresolved computed/indirect loading fails closed. Exact primitive network and CoinDCX crypto-owner lists are pinned, so the live directory is not an allowlisted escape hatch. Strategy, research, ranking, risk, generic coin runtime, unrelated app roots, and the Phase 14 paper tree cannot reach the chain.
- **Live-only authority:** `LiveExecutionAuthority` is structurally non-interchangeable with the Phase 14 paper authorities — a different class, a different private field, a module-private issuer symbol, and no cast, flag or mode that converts one into the other. It is minted only by a composition that first proves genuine Phase 12 research approval (OPEN), a genuine kernel origin, and a genuine Phase 13 admission, and it binds the exact intent, account, pair and risk decision it was issued for.
- **Authoritative economics:** quantity, leverage, risk decision id and admission id are read from the accepted risk decision itself; a caller supplies only non-economic order shape, which is then validated against a content-addressed execution policy and the authoritative CoinDCX instrument metadata. Quantity always floors to the instrument increment and a limit price always quantizes away from crossing, so no quantization step can increase risk.
- **Deterministic identity:** the intent id is a canonical hash over every outcome-relevant field, and the client order id is derived from the same preimage in a separate hash domain under a documented 36-character `p17-<32 hex>` adapter policy. No clock, random value, insertion order or database sequence participates.
- **Acknowledgement is not fill:** ten explicit states (including `RECONCILIATION_REQUIRED`) with a validated transition relation. Cumulative fill is monotonic, partial fills are first class, a cancel acknowledgement never erases confirmed fills, and a cancel that races a complete fill resolves as `FILLED`.
- **Fail-closed ambiguity:** a create-order mutation whose outcome cannot be established becomes `SUBMISSION_AMBIGUOUS` with a durable fault and is never resent, never assumed failed, never assumed succeeded, and never given a fabricated exchange order id. Resolving it is Phase 18 reconciliation, which Phase 17 deliberately does not implement.
- **Observation pagination:** the adapter requests 200 rows but does not claim that futures supports or guarantees that page size. It follows every non-empty page, treats only an empty page as current exhaustion evidence, retains at most one exact exchange-id match, rejects duplicate matches, and returns explicit ambiguity if its fixed 100-page guard is reached.
- **CLOSE depends on Phase 18 position establishment:** Phase 17 consumes authoritative durable `live_position` ownership and revision but contains no production venue-to-table writer. Until Phase 18 establishes/reconciles that row, production CLOSE fails with `LIVE_POSITION_NOT_AVAILABLE` before authority mint or exchange mutation. Test-only seeding proves authorization mechanics, not production readiness.
- **Database-enforced idempotence:** primary-key intent identity, unique client order id, a conditional single-winner dispatch claim, revision-guarded state commits, and a unique observation digest for repeated provider events. Proven against a real disposable MySQL database over two independent connections, not only in memory.
- **Credential isolation:** the trusted composer passes configured key/secret through the gateway constructor; only the mutation transport retains them and constructs signatures/authentication headers. No gateway result, error, audit record or log line can carry them, including hostile JSON-encoded provider errors, and a live execution error refuses construction if its structured details name a sensitive key at any depth.
- Complete specification, CoinDCX endpoint evidence with confidence labels, and the honest verification-status matrix are in `docs/PHASE17_LIVE_EXECUTION.md`.

### 2.21 Reconciliation & Crash Recovery (Phase 18)
- The durable answer to one question asked before every normal Phase 17 live mutation (OPEN, ordinary cancel, CLOSE): *may this account mutate exchange state right now?* Phase 17 made the system mutation-capable and deliberately left restart reconciliation unresolved; Phase 18 owns it: it checks durable state against repeated REST reads of the venue and blocks the account whenever they disagree or the evidence is insufficient. Sampled REST state cannot prove account continuity, so a clean result is informational only and normal live mutation stays intentionally unreachable.
- **Fail-closed startup barrier:** every account begins each runtime in a state equivalent to `RECONCILIATION_REQUIRED`, and an absent `live_reconciliation_state` row reads as exactly that — so applying the migration alone cannot enable trading anywhere. Five durable states (`RECONCILIATION_REQUIRED`, `RUNNING`, `HEALTHY`, `UNHEALTHY`, `MANUAL_REVIEW_REQUIRED`) gate the normal Phase 17 paths `openLive`, `cancelLive` and `closeLive` (and the venue-read-only `syncLive`); reconciliation-owned orphan cancellation is not gated by them and grants no trading authority. The barrier is an **additional** gate placed before the Phase 17 authority mint: every existing enablement, research, kernel, risk-admission and position-ownership check still runs unchanged, and the barrier can only refuse a mutation, never authorize one.
- **Restart safety is durable, not in-memory:** the authority is the database row; a per-process **runtime epoch** merely binds that row to the process that proved it. A restart mints a new epoch, so a `HEALTHY` verdict left by a previous process no longer satisfies the barrier — without rewriting history, and without the gate ever being satisfiable by process-local state. Clearing the process's memory cannot turn the gate on; only a committed run can.
- **Generation fencing, enforced by MySQL:** `UNIQUE(account_id, generation)` on `live_reconciliation_run` makes exactly one worker the authoritative owner of a generation — the loser's INSERT collides in the database, not in a process-local lock. Every durable write re-reads the state row `FOR UPDATE` and revalidates both generation and epoch against its lease inside the same transaction, so a stale worker cannot commit on any path. Claiming immediately withdraws `healthy_generation`, which is what makes a mid-run crash safe; the next start fences the dead run as `ABANDONED`.
- **Evidence carries provenance and a conservative completeness flag:** order and position reads reuse the frozen Phase 2 authenticated read endpoints — Phase 18 adds no endpoint, no signing site, and no HTTP owner. Each read keeps its own window plus an explicit `complete` flag, and **only** an empty page is treated as exhaustion (an inference from the documented pagination contract, not a provider guarantee). A short non-empty page, a pagination guard, or any provider failure yields `complete: false` with a named reason, and absence in such a read is never treated as proof that an order never existed. Conservation arithmetic, causal ordering, account identity and conflicting duplicates are all re-proven in the domain, with no tolerance bands.
- **The TOCTOU limitation is disclosed, not hidden:** CoinDCX exposes no atomic multi-endpoint snapshot, so the orders read and the positions read are two different instants. The two windows are never described as one; where they overlap, or where the venue provably moved between them, the run records a blocking causality finding and the account is **not** declared healthy.
- **Ambiguous creates are adopted only by an exact provider `client_order_id` match:** the deterministic 36-character client order id is now sent on every create as CoinDCX's provider-confirmed idempotent `client_order_id`, and List Orders returns it. `resolveAmbiguousCreate` first looks for venue orders carrying that exact id (strict string equality; a venue `null` never matches). Exactly one match, in a complete read, unclaimed, economically consistent and inside the submission window, is adopted as `RECON_AMBIGUOUS_CREATE_RESOLVED_BY_CLIENT_ORDER_ID` — order identity only, never account continuity. Two or more matches are `RECON_CLIENT_ORDER_ID_DUPLICATE_AT_VENUE` (manual review). With no match, economic matching is still refused outright: time-in-force is not provable (the futures List Orders contract documents no time-in-force field, and a missing field is never treated as a match), so the order gets the `MANUAL_REVIEW_REQUIRED` finding `RECON_AMBIGUOUS_CREATE_IDENTITY_UNOBSERVABLE` exactly as before: no venue order id is bound, no economic effect is applied, and the order stays reconciliation-required until a human resolves it. A provider duplicate-id create failure is a typed fail-closed outcome that never resolves anything by itself, and no duplicate error code is assumed until CoinDCX confirms it.
- **Provider account identity is a fail-closed guard, not continuity:** live enablement requires `COINDCX_EXPECTED_ACCOUNT_FINGERPRINT` (SHA-256 of the expected `/users/info` `coindcx_id`, which CoinDCX confirms is permanent across API-key rotation and distinct per subaccount). Every reconciliation run verifies it before any durable read, recovery, evidence read or effect; a mismatch is `RECON_ACCOUNT_IDENTITY_MISMATCH` (manual review) and a missing or unreadable identity is `RECON_ACCOUNT_IDENTITY_UNVERIFIED`. Success proves only which trading account the credentials act on at read time. CoinDCX exposes no API-key generation identity, so none is claimed, and `currentAccountContinuityCapability()` is unchanged.
- **Ambiguity is never resent:** an ambiguous cancellation resolves from the venue's own view of the exact order id — cancelled, filled, or still resting — and is never automatically resent merely because the process restarted. Phase 17's durable cancel claim and generation are preserved untouched.
- **Ownership is derived upward from lineage, never downward from the aggregate:** an exchange aggregate position alone does NOT prove strategy-instance ownership, and CoinDCX never reports which strategy opened a position. Ownership comes only from exact Phase 17-verified accepted-fill lineage and must reconcile exactly to the venue aggregate. A lone strategy is never handed a residual it cannot prove; several instances whose shares sum exactly are fully attributed, but because Phase 17's `live_position` is a single-owner record, it is deliberately left unwritten and CLOSE for that pair stays fail-closed rather than letting one owner claim the aggregate.
- **Conservative by construction:** seven classification categories, of which only `VERIFIED_MATCH`, `SAFE_AUTHORITATIVE_ADVANCE` and `LOCAL_INCOMPLETE_BUT_PROVABLY_RECONSTRUCTABLE` permit health. Reconciliation never lowers a cumulative fill, never rewrites a settled terminal order, and never repairs data merely to make the database equal the exchange. A finding's `blocking` column defaults to true, so a new category cannot silently permit trading.
- **Orphans are never adopted:** an active venue order with no proven local lineage is classified explicitly and never attached to the nearest local intent. Cleanup is disabled by default, requires the exact lowercase `true` plus an account allowlist, persists its claim before the wire call, binds the exact venue order id, and travels the approved Phase 17 gateway rather than introducing a second raw-network mutation owner. An ambiguous cancellation outcome becomes a sticky, blocking manual-review finding and is never retried. With cleanup off, the orphan still blocks live trading. Orphan cancellation is a **separate, reconciliation-owned remediation path, not normal trading authority**: it runs inside a reconciliation run and does not pass `requireCurrentReconciliation`, so it grants no OPEN/cancel/CLOSE authority, proves nothing about account continuity, and does not make live authorization ready. It is bounded instead by the orphan-cleanup policy (explicit enablement, account allowlist, a 1..20 per-run ceiling), reconciliation account/generation fencing, and durable claim → arm → wire ordering.
- **Idempotence is database-enforced:** unique observation digests prevent duplicate fills and events, `UNIQUE(account_id, finding_sha256)` turns a rerun into a generation-window update rather than a duplicate fault, the conditional orphan claim prevents a second cancel, and an unchanged lineage digest short-circuits the write so reruns produce no revision churn. Findings deliberately exclude the generation from their identity, and stop blocking once a newer generation no longer re-observes them — without the historical fact ever being deleted.
- **Ports and adapters:** `src/execution/live/reconciliation/**` depends on three narrow ports and reaches no integration module, no HTTP client, no signer, and no credential — proven over the true transitive import graph. Paper execution remains structurally unable to reach it, and the reconciliation tree contains no coin-specific executable logic.
- **Status: CURRENT. Authoritative account continuity: NOT IMPLEMENTED. Live authorization readiness: NOT READY. LIVE-VENUE VERIFIED: NO.** `currentAccountContinuityCapability()` returns `REST_CURRENT_STATE_OBSERVED`, so `requireCurrentReconciliation` refuses every normal Phase 17 live mutation with `ACCOUNT_CONTINUITY_NOT_PROVEN`, even for a `HEALTHY` account. A provider-contract review found partial primitives only: authenticated `/users/info` can attest the provider account id (`coindcx_id`) at a point in time (Level A), but no provider credential-generation or session identity (Level B) and no gap-free account-state continuity through mutation authorization (Level C) is documented or proven, so full authoritative continuity cannot be established today (`docs/PHASE18_RECONCILIATION.md` §6.4.5). The automated suites are unit-level and real-MySQL evidence with the venue faked; none is live-venue proof.
- Complete specification, the honest verification-status matrix, and the explicit list of what a real venue would still have to confirm are in `docs/PHASE18_RECONCILIATION.md`.
